# Bottleneck Analysis

## 1. Вичерпання пулу з'єднань Postgres при горизонтальному масштабуванні API

**Компонент / Операція / Запит:** Будь-який запит, що використовує
`DatabaseSession` (SQLAlchemy async engine, `shared/db/db.py`).

**Причина (Root Cause):** Розмір пулу з'єднань (`DB_POOL_SIZE` +
`DB_MAX_OVERFLOW`) фіксується **на процес**, а не на кластер. Стеля
одночасних з'єднань до Postgres — `(DB_POOL_SIZE + DB_MAX_OVERFLOW) × кількість
процесів` (реплік `api` + `celery-worker`). Масштабування `api` командою
`docker compose up --scale api=3` без відповідного зменшення пер-процесного
пулу або збільшення `max_connections` на самій БД лінійно множить навантаження
на Postgres.

**Симптоматика та прояв:** При наближенні до стелі — зростання `p95`/`p99`
latency запитів на очікування вільного з'єднання з пулу (SQLAlchemy
`QueuePool` timeout), а при повному вичерпанні — помилки `too many
connections` безпосередньо від Postgres і 500-і на клієнті. Connection Pool
Exhaustion — типова точка деградації саме після горизонтального
масштабування compute-шару, а не до нього.

## 2. Redis без обмеження пам'яті при сплеску запису одним клоном

**Компонент / Операція / Запит:** `POST /memories/write` → `shared.streams.append_memory`
(`XADD` у `clone-stream:{clone_id}`).

**Причина (Root Cause):** `MEMORY_STREAM_MAXLEN` — це поріг, після якого
асинхронно запускається позаплановий flush, а не жорсткий ліміт Redis
(`XADD ... MAXLEN`), тобто між моментом перевищення порогу і фактичним
завершенням фонового flush стрім продовжує приймати нові записи. Сам
Redis-сервер налаштований без `maxmemory` (лише `noeviction` за замовчуванням).

**Симптоматика та прояв:** У сценарії короткого, дуже інтенсивного сплеску
запису від одного клона (набагато швидше, ніж встигає відпрацювати
`flush_clone_stream`) — необмежене зростання `used_memory` Redis
(`INFO memory`), що при відсутності стелі закінчується OOM-вбивством
контейнера ОС і втратою ще не зафлашених записів цього клона (пом'якшено
`--appendonly yes`, але відновлення після OOM все одно вимагає перезапуску).

## 3. nginx як єдина точка входу без резервування

**Компонент / Операція / Запит:** Весь зовнішній трафік — `infra-nginx-1`,
єдиний reverse-proxy контейнер перед пулом `api`.

**Причина (Root Cause):** Конфігурація описує один-єдиний nginx-контейнер без
будь-якого механізму резервування (Keepalived/VRRP, DNS Round Robin,
множинні edge-instances). Це Single Point of Failure на рівні
інфраструктури, незалежно від того, наскільки сам `api`-шар масштабований і
stateless.

**Симптоматика та прояв:** Падіння або перевантаження одного контейнера
nginx миттєво й повністю зупиняє обслуговування зовнішніх запитів (100%
error rate ззовні), навіть якщо всі репліки `api` та обидві БД повністю
працездатні — класична демонстрація різниці між "backend масштабований" і
"система відмовостійка в цілому".
