# Resilience Profile

Зведена картина того, **що саме відбувається, коли ламається окрема частина
системи**. Кожен рядок позначено: *виміряно* — відтворено на живому стеку й
зафіксовано в README відповідної лаби; *за кодом* — випливає з реалізації, але
окремо не вимірювалося.

## 1. Відмова компонента

| Що впало | Що бачить клієнт | Що працює далі | Статус | Лаба |
| --- | --- | --- | --- | --- |
| Один екземпляр `api` | запити перенаправляються на інший, 0 помилок 5xx | усе | виміряно | 3 |
| nginx | повна недоступність (єдина точка входу, SPOF) | — | за архітектурою | 3 |
| Redis (кеш) | `GET /memories/backups` 200 (`X-Cache: BYPASS`), `GET /fleet/leaderboard` 200 (обчислення без захисту) | читання | виміряно | 4, 8 |
| Redis (потік запису) | `POST /memories/write` → **503** `Retry-After` за ≈1 с (раніше 500 + reset з'єднання, що виводило інстанси з nginx) | читання (0 % помилок), авторизація | виміряно під навантаженням (лаба 10) | 1, 8, 10 |
| Репліка Postgres | читання йдуть на primary (`X-DB-Node: primary-fallback`), `/health` 200; під навантаженням ≈1,3 % помилок за вікно виявлення | усе | виміряно (лаби 6, 10) | 6, 10 |

## 2. Навантажувальні патерни

| Патерн | Наслідок без захисту | Захист | Результат |
| --- | --- | --- | --- |
| Cache stampede (500 VUs, ключ щойно прострочено) | кілька однакових агрегатів паралельно (6–8), до 17.6% помилок 502 за повільного запиту | single-flight + Redis lock / SWR | 1 обчислення, 0 помилок, ×2 RPS |
| Cache avalanche (60 ключів з однаковим TTL) | 49–53 обчислень за секунду | TTL jitter ±30% | 13–18 за секунду |
| Cache penetration (відсутні id) | 1 056–1 486 запитів до БД на 1 500, вичерпання пулу, 500 | negative cache + Bloom filter | 0–5 запитів до БД |
| Холодний старт під піковим навантаженням | 30–41% 502, 400+% CPU control-БД (шторм нових з'єднань) | прогрів пулів перед трафіком | чисті прогони після прогріву |
| Hot shard (один тенант) | 87% читань на одному шарді | hash / virtual buckets | 52/48 |
| Stale read після запису | читання попереднього значення з репліки | read-after-write вікно в Redis | 0 застарілих читань власних змін |

## 3. Режими деградації

| Режим | Умова | Поведінка |
| --- | --- | --- |
| Normal | усе працює | читання з реплік і кешу, запис через Redis → шарди |
| Read-only | primary недоступний | `GET` з репліки, мутації 503 з `Retry-After` |
| Degraded reads | репліка недоступна | усе читання з primary, breaker 5 с |
| Cache-less | Redis недоступний | читання напряму з БД, **без захисту від stampede**, запис недоступний |
| Partial fleet | шард недоступний | клони на живих шардах працюють, глобальні агрегати недоступні |

## 4. Відомі прогалини (чесний список)

1. **Запис повністю залежить від Redis**: немає локального буфера/черги на
   випадок його падіння (`POST /memories/write` → 503 за ≈1 с).
2. **Глобальні агрегати все-або-нічого**: один недоступний шард робить
   `/fleet/leaderboard` і `/admin/backups` недоступними; часткова відповідь з
   позначкою не реалізована.
3. **Автоматичного failover primary немає** (promote — ручний крок, потрібен
   Patroni/Raft-менеджер).
4. **Живої міграції даних між шардами немає** — лише модель і процедура (лаба 7).
5. **nginx — SPOF**; для вилучення потрібні Keepalived/VRRP або кілька LB.
6. **Блокування кешу — оптимізація, не гарантія** (один Redis, не Redlock з
   кворумом); для коректності, що має триматися, не підходить.
7. **Холодний старт** не має readiness-перевірки прогрітого пулу.
8. **Id резервних копій унікальні лише в межах шарду** (потрібні ULID/діапазони).
9. **Немає breaker для primary**: при його падінні кожен запит чекає
   `DB_CONNECT_TIMEOUT` (3 с) перед переходом на репліку (p99 ≈3 с).
10. **Бюджет з'єднань Postgres**: з пулами за замовчуванням (10+5 на процес)
    4 інстанси ×2 воркери перевищують `max_connections=100` (виміряно: «too
    many clients», 75 % помилок читання); потрібні менші пули або PgBouncer.
11. **Пасивні health-перевірки nginx з двома інстансами**: три помилки з'єднання
    за 15 с виводять обидва з ротації. Застосунок тепер віддає 503 замість 500,
    але сама схема крихка (лаба 10, `docs/final-architecture.md` §6).
